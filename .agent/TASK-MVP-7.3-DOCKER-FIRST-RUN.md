## Зачем

Владелец впервые запустил проект командой `docker compose up -d --build` (Windows, Docker Desktop, песочница T-Invest, реальный токен). Ни тесты, ни независимые живые прогоны на чистом окружении этого не ловили; на реальном запуске нашлось восемь проблем (см. ниже). Пока они не исправлены, первый ручной прогон песочницы (события `OrderStateStream`, поведение сделки при удалении заявок песочницей) через интерфейс невозможен.

Это исправления дефектов, не новая семантика. Контракты D/C/S/N/L/E/R/U/I не меняются.

## Найденные проблемы и требуемое исправление

### P1. Фронтенд не ставит `Content-Type: application/json` (блокирующая)
`frontend/src/api.ts`: `post`/`put`/`patch` шлют `JSON.stringify(...)` без заголовка, браузер уходит с `text/plain`. Свежие версии FastAPI строго проверяют `Content-Type` и тело воспринимается строкой. Симптом: пополнение песочничного счёта показывает `model_attributes_type ... "input":"{\"account_id\":...}"` (тело пришло строкой). Ломаются все записи из интерфейса.
Исправление: заголовок `Content-Type: application/json` для запросов с телом (в `request`/`api.*`, без дублирования). Тест vitest: заголовок реально уходит в `fetch` для post/put/patch; для `post` без тела и `get` заголовка нет.

### P2. Зависимости бэкенда не зафиксированы
`backend/pyproject.toml`: `fastapi>=0.115`, `uvicorn>=0.30`, `pydantic>=2.7`, `httpx>=0.27` и т. д., lock-файла нет. Образ при каждой сборке получает самые свежие версии, независимые ревью шли на другом наборе версий (именно поэтому P1 не поймали).
Исправление: воспроизводимая сборка образа (lock-файл или constraints, который использует `docker/backend.Dockerfile`; выбор механизма за Кодером, описать в REPORT), версии должны совпадать с теми, на которых прогоняются тесты. Не обновлять версии «заодно».

### P3. `CORS_ORIGINS` разбирается только как JSON
`backend/app/core/config.py`: `cors_origins: list[str]`, комментарий обещает «comma-separated или JSON», но pydantic-settings принимает только JSON. Значение из `.env.example` (`CORS_ORIGINS=http://localhost:5173`) роняет запуск: `SettingsError: error parsing value for field "cors_origins"` (падает `alembic upgrade head`, контейнер бэкенда не стартует).
Исправление: принимать и строку через запятую, и JSON-массив (тот же вопрос для `risk_blocked_instruments`, у которого пустое значение в `.env` не должно ронять запуск). Тесты: оба формата, пустая строка, значение из `.env.example`.

### P4. Контейнер не доверяет корневому сертификату Минцифры
Цепочка `*.tbank.ru` → Russian Trusted Sub CA → Russian Trusted Root CA. В `python:3.12-slim` корня нет; из контейнера: `CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain`, интерфейс показывает «T-Invest connection error: ConnectError». С хоста Windows всё работает.
Исправление: образ бэкенда доверяет корню Минцифры (сертификаты берутся из надёжного источника, зафиксированы в репозитории или скачиваются при сборке с проверкой; способ описать в REPORT), TLS-проверка **не отключается** ни в коде, ни в окружении (`verify=False` и аналоги запрещены). Подключение к T-Invest из контейнера должно работать без ручных правок.

### P5. Ответ `OpenSandboxAccount` разбирается по неверному ключу
`backend/app/brokers/tinvest.py`, `open_sandbox_account`: код читает `data.get("account_id")`, REST T-Invest возвращает `accountId`. Симптом: «OpenSandboxAccount returned no account_id» при том, что счёт на стороне T-Invest создан (появляется после «Синхронизировать счета»).
Исправление: по документации T-Invest проверить имена полей **всех трёх** песочничных вызовов (`OpenSandboxAccount`, `SandboxPayIn`, `CloseSandboxAccount`) — и в запросе, и в ответе (в `SandboxPayIn` ответ с балансом тоже проверить); не гадать, сослаться на документацию в REPORT. Тесты на реальных образцах ответов REST.

### P6. Плашка успеха синхронизации красная
`SandboxPage.tsx`: сообщение «Синхронизировано счетов: N» показывается в стиле ошибки. Исправление: отдельный стиль для успешного сообщения.

### P7. Локальный запуск и документация
- В `README` описать запуск на Windows (PowerShell) и обязательные шаги: `.env` из `.env.example`, `TINVEST_TOKEN`, `TINVEST_SANDBOX=true`; указать, что все порты только на `127.0.0.1`.
- `.gitignore`/`.dockerignore`: не допускать случайного коммита локальных файлов (`certs/`, `docker-compose.override.yml`, `.env`).

### P8. Синхронизация инструментов загружает не только MOEX
Решение владельца (2026-10-07): проект работает **только с инструментами MOEX**. Сейчас «Синхронизировать инструменты» загружает всё, что отдаёт T-Invest: в справочнике иностранные бумаги (например, «CK Hutchison Holdings», SHARE / hkd, лот 10), поле «Биржа» в интерфейсе — `unknown` (`brokers/tinvest.py`: `exchange=raw.get("exchange")`).
Исправление: по документации T-Invest определить, какие поля инструмента (`exchange`, `classCode`, `currency`, `countryOfRisk` и т. п.) надёжно отличают бумаги MOEX, **в том числе в песочнице**, где значения могут отличаться от боевого контура; применять фильтр при синхронизации и показывать в интерфейсе осмысленную биржу. Критерий фильтра не придумывать: если документация или реальные ответы песочницы не дают однозначного признака — остановиться на этой границе, описать в REPORT (с образцами реальных ответов) и спросить владельца. Уже загруженные нерелевантные записи при повторной синхронизации не должны оставаться «активными» в списках выбора (способ описать в REPORT; миграции данных без необходимости не делать).
Тесты: фильтр на реальных образцах ответов (MOEX-бумага проходит, иностранная нет), поле биржи.

## Критерий приёмки (живой прогон обязателен, `AGENTS.md` / REVIEW)

С нуля, на чистом томе PostgreSQL, **без каких-либо ручных правок `.env`, кроме токена**:
1. `docker compose up -d --build` → все четыре контейнера работают, бэкенд применил миграции до актуальной.
2. Интерфейс: «T-Invest: Подключено», «Синхронизировать инструменты» загружает справочник **только с инструментами MOEX** (P8).
3. «Песочница и счета»: открыть песочничный счёт (без ошибки) → пополнить → баланс отображается после синхронизации.
4. Из интерфейса: создать стратегию, создать бота, запустить бэктест (запись работает).
5. Повтор на второй машине/профиле не требуется, но сборка должна быть воспроизводимой (P2).

Проверка Claude: независимый прогон на чистом окружении + при необходимости имитация версий FastAPI (до и после строгой проверки `Content-Type`).
