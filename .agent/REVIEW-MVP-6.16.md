## Что сделано правильно

- **E1**: формула общая для Live и Backtest (`simple_stop_level` + `stop_distance_percent`). `sl_offset` = offset последнего уровня − offset уровня 0; для «Простого» это ровно перекрытие (offset уровней считается от одной опорной цены). P0 — средневзвешенная цена исполнения уровня 0, при восстановлении берётся из `average_fill_price`. Округление LONG вверх / SHORT вниз, нет тика → `DealTickSizeInvalid`. Активация только при всех уровнях FILLED.
- **E2 (выставление/перевыставление)**: порядок Risk → отмена → подтверждение → перечитать позицию → выставить; объём — вся позиция вниз до лотов; повторная проверка Risk, если объём после отмены изменился; одна заявка одновременно; исполнение во время отмены (`DealStopExecuted`) закрывает сделку как `stop_loss`. Закрытие по TP отменяет стоп с подтверждением; закрытие по стопу отменяет TP.
- **Адаптер**: `PostStopOrder` (STOP_LOSS, GOOD_TILL_CANCEL, EXCHANGE_ORDER_TYPE_MARKET, лоты, Quotation, UUID-ключ), `CancelStopOrder`, маппинг статусов без угадывания (неизвестный → `UNKNOWN`). Типы T-Invest не выходят из адаптера.
- **E3/E4**: `stop_bot_after=None` → 409; `signal_stop` и прочие режимы по-прежнему 409; простой SL + простой TP + «Простой»/«Свой» принимаются.
- **E5**: бэктест считает от P0 (`grid_state.reference_price` = цена исполнения входа) с той же формулой и включает стоп только после сборки сетки; старые тесты бэктеста не менялись.

## Обязательные исправления

### B1 (блокер). Исполненный стоп не виден: `GetStopOrders` без фильтра возвращает только активные заявки

`TInvestAdapter.get_stop_orders()` вызывает `GetStopOrders` только с `accountId`. В официальном контракте T-Invest (`stoporders.proto`) метод описан как «получить список **активных** стоп-заявок по счёту»; исполненные, отменённые и истёкшие возвращаются только при явном `status` (`STOP_ORDER_STATUS_ALL` / `_EXECUTED` / …) и границах `from`/`to`. Поэтому на реальном брокере статус `EXECUTED` никогда не придёт, и исполненный стоп выглядит как «отсутствующий». Фейковый брокер в тестах возвращает все заявки со статусами, поэтому тесты этого не видят.

Проба ревьюера (фейк, который, как T-Invest, отдаёт только активные; стоп исполнен, брокер сообщает нулевую позицию):

| Порядок событий в стриме | Результат |
|---|---|
| позиция в `PositionManager` ещё 435 | `check_stop_orders` видит «отсутствует» → `_rearm_stop` **выставляет новую стоп-заявку SELL 435 @ 80.0 на уже пустой позиции**. Цена уже ниже 80, значит заявка сработает сразу и откроет **SHORT 435**. Сделка OPEN. |
| позиция уже 0 | сделка CLOSED с `close_reason=None` (не `stop_loss`), колбэк E3 не вызван → `stop_bot_after=true` **игнорируется**, бот продолжает торговать |

Тот же путь в восстановлении D5: исполненная заявка не найдена → `sl_order_id=None` → позиция 0 → закрытие как `take_profit`.

Что нужно:

1. Получать статус своей заявки так, чтобы исполненная/отменённая/истёкшая были видны: `GetStopOrders` с `status=STOP_ORDER_STATUS_ALL` и разумными `from`/`to` (например, от времени выставления заявки сделки, чтобы не тянуть всю историю счёта). Способ — на усмотрение Кодера, но только по официальной документации T-Invest; сослаться на неё в §34.
2. «Заявки нет у брокера» — это неизвестное состояние, а не повод выставить новую. Перед любой повторной выставкой при «отсутствии» сверить **позицию у брокера** (`get_open_positions`), а не только `PositionManager`. Позиция у брокера 0 → не выставлять; связать со стопом нельзя → ERROR (E2). Это касается и живого пути (`check_stop_orders`), и восстановления (E2: «выставить один раз **после успешной сверки**»).
3. Фейк в тестах должен вести себя как T-Invest: без `status` — только активные. Добавить тесты на оба порядка событий из пробы выше и на восстановление после исполнения стопа.

### B2. Сбой остановки бота после стопа тихо проглатывается

`_close_deal` вызывает `on_stop_loss` в `try/except Exception: pass`. Если `runtime.stop()` или `update_state` упадут, бот с `stop_bot_after=true` останется RUNNING и откроет следующую сделку — прямо против настройки E3. Нужно: при ошибке колбэка бот уходит в ERROR через существующий путь B2 (`on_bot_error`), причина видна в API; тест.

### B3. Пустой `stopOrderId` принимается как ACTIVE

`place_stop_order` при ответе без `stopOrderId` возвращает `ACTIVE` с `order_id=""`. Затем заявка считается «отсутствующей» и попадает в путь B1. Нужно: нет идентификатора → `UNKNOWN` (`DealReconciliationRequired` → ERROR); тест маппинга.

## Наблюдения (не блокеры, на решение Кодера)

- `check_stop_orders` вызывается после **каждого** сообщения стрима и делает `GetStopOrders` на **каждую** вооружённую сделку. У сервисов T-Invest есть лимиты запросов в минуту, а одна ошибка чтения переводит бот в ERROR. Разумно делать один вызов на счёт за пачку сообщений.
- `_rearm_stop` при нулевой позиции закрывает сделку с `close_reason=None`. Если исправление B1 оставит этот путь, причину лучше указать явно или перевести в ERROR.
