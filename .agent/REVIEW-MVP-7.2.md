## Блокер

### B1. Нулевой и отрицательный период (и целые параметры) проходят валидацию, а расчёт падает

До MVP-7.2 `period = 0` молча заменялся запасным значением (`0 or 20`). Теперь запасных значений нет, а проверка `validate_spec_args` смотрит только на наличие (`None`), поэтому:

- `POST /api/strategies/validate` с RSI `period: 0` и `period: -5` → `{"valid": true}`; `POST /api/strategies` с `period: 0` → **201** (сохранилось);
- `indicator_series("SMA", …, 0, …)` и `("RSI", …, 0, …)` → **`ZeroDivisionError`** (проверено прямым вызовом на 80 барах); `period=-3` → тихо возвращает пустой результат (`None`); MACD `fast=0` считается без ошибки;
- форма (`frontend/src/lib/…`, `FilterGroupEditor.tsx`) тоже пропускает `0` и отрицательные значения.

Итог: ошибка, которую раньше скрывал запасной вариант, теперь всплывёт не при сохранении, а в бэктесте (500) или в живом цикле бота (ошибка расчёта). Это прямое следствие снятия запасных значений; пользователь не должен получать падение расчёта на значении, которое сам же ввёл.

Нужно (границы допустимых значений — только математическая необходимость, **не** диапазоны Veles и не новая семантика):
1. `validate_spec_args`: период (если `uses_period`) и целочисленные параметры каталога (`type == "int"`) должны быть целыми **≥ 1**; иначе `ValueError` с русским сообщением, например «Индикатор RSI: параметр «период» должен быть целым числом не меньше 1.». Параметры типа `float` (k) на положительность не ограничивать — это решение по семантике, а не по математике расчёта (при `k = 0` расчёт не падает).
2. Форма: те же правила → ошибка у поля, отправка блокируется.
3. Тесты: `validate_spec_args` и `POST /api/strategies/validate` для `0` и `-5` (период) и `fast = 0` (MACD) → 422; vitest для формы (поле с `0` блокирует отправку).
