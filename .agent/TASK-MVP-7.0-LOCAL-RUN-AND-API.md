## Зачем

Сейчас проект нельзя «пощупать»: токен T-Invest не попадает в контейнер, миграции запускаются руками, нет API для создания стратегии и бота, нет песочницы, бэктест доступен только из кода. Владелец решил (2026-10-05):

- две задачи: **MVP-7.0** — запуск и backend API (эта задача), **MVP-7.1** — экраны;
- редактор стратегии в MVP-7.1 — **полная форма**, как в Veles (поэтому в 7.0 нужен машиночитаемый формат конфигурации);
- бэктест запускается из интерфейса;
- песочница T-Invest готовится кнопками в интерфейсе (в 7.0 — API для них).

Интерфейс (React) в эту задачу **не входит**.

## Утверждённый контракт (владелец, 2026-10-05)

Ничего сверх R1–R8 не придумывать. Семантику Veles не менять. Если чего-то не хватает, остановиться на границе, описать в REPORT и спросить.

### R1. Запуск одной командой (Windows, Docker Desktop)

- `.env.example` в **корне** репозитория: `TINVEST_TOKEN=`, `TINVEST_SANDBOX=true`, `LIVE_TRADING_ENABLED=false` и прочие нужные переменные с комментариями по-русски. `.env` — в `.gitignore`.
- `docker-compose.yml`: сервис `backend` читает корневой `.env` (`env_file`); без `.env` приложение всё равно стартует (интеграция T-Invest — `not_configured`, как сейчас).
- Все порты публикуются только на `127.0.0.1` (postgres, redis, backend, frontend). API без авторизации и не должен быть доступен из сети.
- Backend при старте контейнера выполняет `alembic upgrade head`, затем `uvicorn`. Ошибка миграции → контейнер не стартует (без молчаливого продолжения).
- `README.md`: раздел «Быстрый старт (Windows)» — PowerShell: клонировать, `copy .env.example .env`, вписать токен песочницы, `docker compose up -d --build`, открыть `http://localhost:5173` и `http://localhost:8000/docs`. Где взять токен песочницы — ссылка на официальную документацию T-Invest.
- Значения по умолчанию в `.env.example` — безопасные: песочница включена, живая торговля выключена.

### R2. Счета

- `POST /api/accounts/sync` — читает счета брокера и сохраняет/обновляет их в таблице `accounts` (`broker`, `external_account_id`, `name`). Повторный вызов не создаёт дублей.
- `GET /api/accounts` уже есть (данные брокера); добавить признак, сохранён ли счёт локально, и его локальный `id` (нужен для бота).

### R3. Песочница T-Invest

- Работает только при `TINVEST_SANDBOX=true`; иначе — 409 с явной ошибкой.
- `POST /api/sandbox/accounts` — открыть счёт песочницы (`SandboxService/OpenSandboxAccount`), сразу синхронизировать его в `accounts` (R2).
- `POST /api/sandbox/accounts/{external_id}/pay-in` — пополнить (`SandboxService/SandboxPayIn`). Сумма и валюта — **обязательные** поля запроса; значения по умолчанию не придумывать.
- `DELETE /api/sandbox/accounts/{external_id}` — закрыть (`CloseSandboxAccount`).
- Типы T-Invest — только в адаптере; наружу — брокер-нейтральные методы/DTO.
- По официальной документации T-Invest проверить, какие сервисы доступны на хосте песочницы для нашего пути: заявки, **стоп-заявки** (MVP-6.16), стримы, торговый статус. Результат с ссылками — в REPORT и в документации. Если чего-то в песочнице нет (например, стоп-заявок), START такого бота в песочнице → 409 с понятной причиной, без обходов.

### R4. Стратегии

- `POST /api/strategies` — `{name, description?, config}`; `config` проверяется `StrategyConfig`; создаются `Strategy` и `StrategyVersion` v1. Ошибка проверки → 422 с перечнем полей.
- `GET /api/strategies`, `GET /api/strategies/{id}` (с последней версией), `GET /api/strategies/{id}/versions`.
- `PUT /api/strategies/{id}` — новая конфигурация создаёт **новую неизменяемую** версию (`version + 1`); старые версии не меняются (они могут использоваться ботами и бэктестами).
- `GET /api/strategies/schema` — JSON Schema `StrategyConfig` (из pydantic), чтобы MVP-7.1 строил полную форму. Подписи, единицы и допустимые значения полей должны быть в схеме (`title`/`description`/enum), **без новых значений по умолчанию**: где в `StrategyConfig` поле обязательное или `None`, так и остаётся.
- `POST /api/strategies/validate` — проверить конфигурацию без сохранения; в ответе также результат `validate_live_deal_config()` (поддерживается ли живая торговля и почему нет), чтобы форма заранее показывала ограничения D1/E4.

### R5. Боты

- `POST /api/bots` — `{name, strategy_version_id, account_id, instrument_id, deposit}`; проверки существования; бот создаётся в STOPPED.
- `PATCH /api/bots/{id}` — дополнительно к депозиту можно сменить `strategy_version_id`, но **только** если бот STOPPED и у него нет незакрытой сделки; иначе 409.
- `DELETE /api/bots/{id}` — только STOPPED и без незакрытой сделки; иначе 409.
- Существующие start/stop/emergency-stop и их проверки (D1, E3/E4, Risk) не менять.

### R6. Просмотр сделок бота (только чтение)

- `GET /api/bots/{id}/deal` — текущая незакрытая сделка: статус, направление, P0, средняя цена и объём позиции, уровни сетки (цена, объём, статус, исполнено), TP (цена, объём), стоп (цена, объём, активен ли), `close_reason`, время. Нет сделки → `null`.
- `GET /api/bots/{id}/deals?limit=` — история сделок (новые сверху) с `close_reason`.
- Источник — хранилище Deal (MVP-6.12); ничего не пересчитывать «для красоты».

### R7. Бэктест по API

- `POST /api/backtests` — `{strategy_version_id | config, instrument_id, timeframe, from, to, deposit, maker_fee, taker_fee, slippage}`. Комиссии и проскальзывание — **обязательные** поля (значения не придумывать).
- Свечи — из `MarketDataService`/брокера по существующему пути (без придумывания свечей), кусками по лимитам брокера. Предел объёма — настройка приложения `backtest_max_candles` (ops-параметр); превышение → 422 с понятной ошибкой.
- Запуск синхронный, результат **не сохраняется** в БД в этой задаче. Ответ: сводка `BacktestResult`, сделки (`BacktestDeal`, включая `reason`), ордера и исполнения.
- Нет `tick_size`/`lot_size` у инструмента → явная ошибка (как в live).

### R8. Бэктест считает объём от депозита, как live

Сейчас бэктест берёт фиксированный `BacktestConfig.quantity`. Для запуска из интерфейса это вводит в заблуждение и расходится с принятым контрактом C1–C3 (MVP-6.11) и принципом «Backtest и Live — одна логика».

- Добавить в `BacktestConfig` депозит и `lot_size`; при заданном депозите объём уровней считается **теми же функциями**, что в live (`app/trading/sizing.py`, C1–C3: сумма номиналов = депозит, лоты вниз).
- Старый путь `quantity` оставить только для существующих тестов; API R7 всегда использует депозит.
- Изменённые тесты бэктеста перечислить в REPORT.
