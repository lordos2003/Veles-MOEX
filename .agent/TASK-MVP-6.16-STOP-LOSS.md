## Зачем

После MVP-6.12 живая сделка поддерживает только простой TP. Стоп-лосс отклоняется при START (D1), поэтому мартингейл-сетка без стопа может довести позицию до очень большого плавающего убытка. MVP-6.16 добавляет **простой стоп-лосс** в живую сделку.

## Источники Veles

Справка Veles «Стоп-лосс» (https://help.veles.finance/ru/platform/settings/stop-loss/):

- «Простой стоп-лосс — это рыночный ордер, который выставляется на заданный процент после исполнения **всех ордеров сетки**.» Пример: «при перекрытии сетки 15% и стоп-лоссе 5% срабатывание произойдёт на 20% от цены открытия».
- Стоп не виден на бирже, пока сетка не собрана полностью; на фьючерсах используется биржевой триггерный ордер.
- Можно указать, должен ли бот остановиться после срабатывания стопа.

Проектная спецификация: `docs/architecture/TASK-08-FULL-EXIT-ENGINE-MVP-5.md` §6 (стоп активен после полной сборки сетки, исполнение рыночное).

## Утверждённый контракт (владелец, 2026-10-02)

### E1. Уровень стопа — от цены открытия: перекрытие + SL

- **Цена открытия `P0`** — фактическая средняя цена исполнения первого ордера сделки (уровень 0 Deal).
- **Отступ стопа** = `(offset_percent последнего уровня сетки − offset_percent уровня 0) + SL%`. Для «Простого» это ровно перекрытие + SL; для «Своего» — отступ последнего ордера от первого + SL.
- LONG: `stop = P0 × (1 − отступ/100)`; SHORT: `stop = P0 × (1 + отступ/100)`. Пример Veles: перекрытие 15%, SL 5% → стоп на −20% от `P0`.
- Округление до шага цены (проектное правило, по аналогии с D3): в сторону **более раннего** срабатывания. LONG — вверх, SHORT — вниз. Нет `tick_size` → явная ошибка.
- Стоп **активируется только после исполнения всех уровней сетки** (все ордера сделки FILLED). До этого стоп-заявки у брокера нет.

### E2. Исполнение — стоп-заявка у брокера (T-Invest)

- Новые брокер-нейтральные методы `BrokerAdapter`: `place_stop_order`, `cancel_stop_order`, `get_stop_orders` (имена на усмотрение Кодера). Реализация в `TInvestAdapter` — через официальный `StopOrdersService` T-Invest (`PostStopOrder` / `CancelStopOrder` / `GetStopOrders`): тип **stop-loss с исполнением по рынку**, срок **до отмены**. Маппинг остаётся внутри адаптера. Для `BacktestBroker` — явный `NotImplementedError` или безопасная заглушка, бэктест их не использует.
- Объём стоп-заявки = **вся текущая позиция** из `PositionManager`, округлённая вниз до целых лотов. Никогда не больше позиции.
- Стоп-заявка проходит `RiskManager.check_order()`. Это уменьшающий ордер, поэтому действует исключение D7.
- **Перевыставление**: при любом изменении позиции после активации (частичное исполнение TP) стоп-заявка заменяется на объём новой позиции. Порядок как в D4/B1/B3: сначала проверить новую заявку в Risk, затем отменить старую и дождаться подтверждения, затем перечитать позицию и выставить новую. Две стоп-заявки одновременно не допускаются. При неизвестном результате отмены бот уходит в ERROR (B2).
- **TP исполнился полностью** → отменить стоп-заявку → сделка CLOSED.
- **Стоп сработал** (брокер исполнил рыночную заявку) → отменить TP → сделка CLOSED с причиной `stop_loss` (поле `close_reason` в Deal + миграция `0006`). Исполнение рыночной заявки, порождённой стоп-заявкой, нужно связать со сделкой: через идентификатор, который возвращает брокер, или через сверку позиции и `GetStopOrders`. Если связать нельзя → бот в ERROR, без молчаливого продолжения.
- **Восстановление (D5)**: стоп-заявки сделки сверяются с брокером. Активная остаётся. Исполненная → закрытие сделки, как выше. Отсутствующая при собранной сетке → выставить один раз после успешной сверки. Неизвестное состояние → ERROR.

### E3. Что делает бот после стопа — настройка стратегии

- `StopLossConfig.stop_bot_after: bool | None = None`. Значение по умолчанию не выдумывается: для живой торговли `None` → отказ при START с явной ошибкой (HTTP 409).
- `true` → после закрытия сделки по стопу бот переходит в **STOPPED** штатной остановкой (MVP-6.5); причина видна в API.
- `false` → бот продолжает и ждёт следующий вход из FLAT (новый депозит по C6).

### E4. Что разрешается в живой торговле

- В `validate_live_deal_config()` (D1) разрешить `ExitConfig.stop_loss` (простой, `kind="percent"`) вместе с простым TP и сеткой «Простой»/«Свой».
- `signal_stop`, мульти-тейк, безубыток, сигнальный TP, подтяжка, режим «Сигнал» по-прежнему отклоняются при START.

### E5. Бэктест — та же семантика

В `backend/app/backtest/engine.py` простой стоп сейчас считается **от средней цены** и **не ждёт сборки сетки**. Это расходится с Veles и с принципом «Backtest и Live — одна логика». Привести бэктест к E1: та же формула уровня, активация после исполнения всех уровней, исполнение рыночное на следующем баре (как сейчас). Формулу уровня вынести в одну функцию и использовать и в бэктесте, и в live. Изменённые тесты бэктеста перечислить в REPORT.
