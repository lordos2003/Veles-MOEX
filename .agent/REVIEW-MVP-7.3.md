## Блокер

### B1. P4 не работает: приложение не доверяет корню Минцифры, T-Invest из контейнера недоступен

Проверено владельцем (2026-10-08) на чистой сборке ветки `agent/review/mvp-7.3` @ `687642a` (`docker compose down -v` → `up -d --build`, без `certs/` и `docker-compose.override.yml`):

- интерфейс: «T-Invest: Отключено», «T-Invest connection error: ConnectError»;
- `docker compose exec backend python -c "import httpx; httpx.get('https://invest-public-api.tbank.ru/rest')"` → `httpx.ConnectError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate in certificate chain`;
- в контейнере три файла `russian_trusted_*.crt` лежат в `/usr/local/share/ca-certificates/`, системный набор (`/etc/ssl/certs/ca-certificates.crt`) обновлён.

**Причина.** `httpx` (а значит и `TInvestAdapter`) по умолчанию проверяет TLS по набору `certifi`, а не по системному хранилищу Debian. `update-ca-certificates` на `httpx` не влияет. Рукопожатие через `openssl s_client` (читает системное хранилище) проходит — отсюда ложное подтверждение в отчёте (критерий 2).

**Подтверждение исправления** (владелец, в том же контейнере): с `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` тот же `httpx.get(...)` → `container: 404` (как с хоста), проверка TLS при этом включена.

**Требуется:** сделать так, чтобы приложение в образе по умолчанию использовало системное хранилище с сертификатами Минцифры (ожидаемое решение — `ENV SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` в `docker/backend.Dockerfile`; допустим другой механизм, обоснованный в REPORT). Проверка TLS не отключается. Тест/проверка в образе: из собранного контейнера `httpx.get('https://invest-public-api.tbank.ru/rest')` без каких-либо переменных окружения от оператора и без `docker-compose.override.yml` → любой HTTP-код, а не `ConnectError`. Живой прогон по критерию приёмки повторить **на чистой копии без локальных файлов** (`git status` не должен показывать `certs/`, `docker-compose.override.yml`) и указать это в REPORT.

## Не блокирует: замечания и дефекты для следующего MVP

1. **Кнопка «Проверить» в форме стратегии всегда даёт 422** (`body.exit: Field required`). UI шлёт `{"config": {…}}`, а `POST /api/strategies/validate` ждёт сам конфиг без обёртки. Дефект существует с MVP-7.1 (файлы не менялись в 7.3), «Создать» не затронуто. Отчёт Кодера («дефектов класса первый запуск не найдено») это пропустил.
2. **Сообщения 422 в баннере** при ошибках вне полей (например, не выбран вид тейк-профита) показываются сырым JSON-списком: `[{"type":"union_tag_not_found",…}]`.
3. **Нижняя граница `pydantic-settings`** в `pyproject.toml` осталась `>=2.3`, а `NoDecode` (P3) появился в 2.7. В образе и в тестах lock держит 2.15.0; границу стоит поднять до `>=2.7`.
4. **Пустой ответ брокера** при синхронизации деактивирует все активные записи этого типа (проверено пробой; следующая успешная синхронизация возвращает их). Риск низкий, можно добавить защиту.
5. **Баланс «0» на карточке счёта** (наблюдение Кодера, решение владельца) и осознанный выбор: деактивация, а не удаление, не проверяет, что на инструмент ссылаются активные боты.
